**规格书「明确不做」清单**（PPT 生成、表格识别、用户系统、付费、任务队列、批量处理）目前仍是不做状态——本文档第 5 节给出把其中一部分转为「做」的具体路径。

**与规格书的已有偏差**（拓展时注意同步规格书）：

- `ai-service` 解析接口额外支持图片格式（.jpg/.jpeg/.png/.bmp，走 OCR）；
- 扫描版 PDF 无文本层时逐页渲染走 OCR（`PDF_OCR_MIN_CHARS/MAX_PAGES/DPI`），整份文档无可用文本时解析失败而非静默成功；
- 后端新增 `DELETE /api/files/:fileId` 删除接口、知识库组件、`POST /api/files/search` 全局检索接口；
- 问答接口在未传 `fileId/fileIds` 时自动检索最近 50 篇已解析文档（全库问答）；
- 文件元信息新增 `sha256`（上传幂等去重）字段；
- 大纲生成支持 markdown 层级前缀（#/##/###），条目下一行可用 `>` 前缀注入该节的写作要求（Prompt「特别要求」）；并新增 `POST /api/generate/outline` 主题生成大纲接口（前端「AI 帮我想大纲」）。

## 二、架构与分层约定

```
┌─────────────────────────────────────────────────────────────┐
│ frontend (React+TS, :3000)                                   │
│   App.tsx 路由 → pages/ 页面 → api/index.ts 契约封装         │
│   components/（通用组件）  hooks/useFileStatus（状态轮询）    │
└──────────────┬──────────────────────────────────────────────┘
               │ REST（/api/*，规格 5.2 契约）
┌──────────────▼──────────────────────────────────────────────┐
│ backend (Express+TS, :3001)                                  │
│   routes/ → services/（业务校验+编排）→ ai-client.service    │
│   file.service（PostgreSQL 元信息事实源 + 落盘）             │
│   middleware/rate-limit（固定窗口限流）                      │
└──────────┬──────────────────────────────┬───────────────────┘
           │ REST（/ai/*，规格 6.2 契约）    │ PostgreSQL（files/settings/app_meta/conversations 表）
┌──────────▼──────────────────────────────▼───────────────────┐
│ ai-service (FastAPI, :8000)          │ Redis（db 1：ai:cache:*）│
│   api/（接口层：校验+错误映射）→ core/（纯业务逻辑）          │
│   llm/client.py（LLM 封装）  config.py（env 唯一入口）        │
│   core/cache.py（LLM/检索缓存，fail-open）                   │
└──────────────┬──────────────────────────────────────────────┘
               ▼ 共享目录 backend/data/（docker 挂载 / 本地配同路径；含向量库 vector/）
```

**文件流转**：frontend → backend（上传落盘）→ ai-service（处理，结果写共享 `PROCESSED_DIR`）→ backend（登记 `filePath`）→ 前端经 `/api/download/:fileId` 下载。

**分层规则（拓展时不得违反）**：

1. 前端页面**只调** `api/index.ts` 的方法，不直接拼 URL；错误提示由 `api/http.ts` 拦截器统一弹出，页面只做自愈（如 404 重置）。
2. backend 路由只做参数取用与转发，**业务逻辑全部在 services/**；对 ai-service 的 HTTP 调用**只经** `services/ai-client.service.ts`。
3. ai-service 的 `api/` 只做校验、组装与错误映射，**核心逻辑全部在 core/**。
4. 环境变量：backend 只经 `config/env.ts`、ai-service 只经 `config.py` 读取，业务代码禁止直接访问 `process.env` / `os.getenv`。
5. 跨端类型契约三处同步：`backend/src/types/index.ts`、`services/ai-client.service.ts` 返回类型、`frontend/src/api/index.ts` 接口类型。

## 三、新增功能的端到端流水线

以新增 **Word→PDF 转换** 为例，共七步。任何新功能基本都沿此路径，可裁剪。

### 第 1 步：定契约（先写类型与接口）

- 在 `backend/src/types/index.ts` 增加请求/响应类型；同步更新规格书 5.2 节。
- 决定形态：**同步接口**（转换/生成类，请求-响应一次完成）还是**异步接口**（解析类，先返回 fileId 再轮询状态）。同步接口最简单，异步接口要扩展状态机（见第 4 步）。

### 第 2 步：ai-service 实现核心逻辑 + 接口

1. `app/core/converter.py` 增加 `convert_docx_to_pdf(src_path, dst_dir)`（可用 LibreOffice headless 子进程调用），返回 `{filename, filePath}`，异常统一 `RuntimeError`。
2. `app/api/convert.py` 增加 `POST /ai/convert/docx2pdf` 路由：校验扩展名 → 保存上传文件 → 调 core → 错误映射（`ValueError`→400、`RuntimeError`→422/502）。
3. `app/main.py` 无需改（convert router 已注册），但若新建独立 api 模块需在此注册并加 `/ai` 前缀。

### 第 3 步：backend 增加服务与路由

1. `services/ai-client.service.ts` 增加 `convertDocxToPdf(file)` 方法（复用 `buildFormData` / `request`）。
2. `services/convert.service.ts` 增加编排：校验扩展名 → 调 ai-client → `fileService.saveAsConverted(file, result.filePath)` 登记元信息 → 返回 `{ fileId, downloadUrl }`。
3. `routes/convert.routes.ts` 增加 `POST /api/convert/docx2pdf`（复用 multer 内存存储与大小校验）。
4. `app.ts` 注册路由（若新开 router 文件）。

### 第 4 步：frontend 增加页面与入口

1. `api/index.ts` 增加 `convertDocx(file)` 方法与类型（与后端契约一致）。
2. `pages/ConvertPage.tsx` 增加 tab 或新页面（新页面更清晰）：`pages/WordToPdfPage.tsx`，结构可整体照抄 ConvertPage（上传 → 转换 → ResultDownload）。
3. `App.tsx` 增加路由；`pages/Home.tsx` 的 `features` 数组增加入口卡片（icon/color 语义色在此统一定义）。

### 第 5 步：异步流程则扩展状态机

若新功能耗时不可控（>2 分钟）需要异步化，参照解析链路：

- backend 路由：落盘后立即返回 `{ fileId }`，`void xxxInBackground(...)` 后台执行（参照 `routes/upload.routes.ts` 的 `parseInBackground`）；
- 状态机（`backend/src/types/index.ts` 的 `FileStatus`）：必要时增加中间态，如 `parsing → converting`，并同步 `frontend/src/api/index.ts` 的 `FileInfo`；
- 前端轮询直接复用 `hooks/useFileStatus.ts`（2s 间隔、3min 上限、404 自愈），展示复用 `components/ParseStatus.tsx`（若状态文案不同可加 prop 或新组件）。

### 第 6 步：文件与元信息落库

两种既有模式，二选一：

- **有原始上传文件**：`fileService.saveAsConverted(originalFile, processedPath)`（status=converted，保留原文件供回退下载）；
- **无原始文件**（如纯生成类）：`fileService.saveGenerated(fileId, filename, processedPath)`（originalPath 直接指向结果）。

结果文件由 ai-service 写入共享 `PROCESSED_DIR`，backend 登记其返回的 `filePath`，**不做复制**（docker 下靠挂载，本地开发靠两端 env 指向同一路径）。

### 第 7 步：验证清单

- [ ] curl 冒烟：ai-service 接口（8000）→ backend 接口（3001）→ 下载接口；
- [ ] 前端完整流程（含错误路径：超大文件、错误格式、ai-service 未启动时的 502 提示）；
- [ ] 删除联动：删除该文件后 ai-service 向量库/文件副本一并清理；
- [ ] docker 下路径一致性（`docker-compose up` 后复测转换/生成/下载）；
- [ ] 同步规格书 5.2 / 6.2 契约、README 功能列表。

## 四、必须遵守的既有约定（坑点清单）

以下都是踩过坑后固化的约定，**新增功能不得绕过**：

1. **双 fileId**：对外 fileId（backend 生成）与 aiFileId（ai-service 解析返回，chroma collection 名/RAG 检索键）不同。问答/摘要转发必须用 `meta.aiFileId ?? meta.fileId`（见 `services/qa.service.ts`）。
2. **PostgreSQL 是元信息事实源**：所有元信息读写走 `fileService`，底层为 PG 的 `files` 表（表结构与 created_at/parsing/dedup 三个索引统一在 `db/schema.ts` 定义，新增列/索引不得散落各处）；创建类写操作收口在 `writeMeta()`（单 INSERT 出口）。**去重索引是非唯一部分索引**（`WHERE sha256 IS NOT NULL AND status <> 'failed'`），因为 `saveAsConverted` 故意不去重——切勿改成唯一索引，否则 PDF→Word 转换会 503。PG 故障一律 503（fail-fast，元信息不可降级）；「读-改-写」仍非事务（单进程 MVP 可接受）。旧 Redis 键（`backend:files:*`）与 files.json 仅作一次性迁移源与回滚冷备份（见 `redis-import.service.ts`，迁移标记在 `app_meta` 表）。
3. **状态机**：`uploaded → parsing → parsed / failed`；转换/生成类直接 `converted`。前端 `useFileStatus` 只在 `parsed`/`failed` 停轮询。
4. **共享目录**：ai-service 写结果到 `PROCESSED_DIR`，backend 直接登记路径供下载。本地开发两端 `UPLOAD_DIR`/`PROCESSED_DIR` 必须配成同一绝对路径（详见部署指南）。
5. **删除联动**：删文件要清四处——Redis 元信息（meta + index/parsing 索引 + dedup 字段）、backend 文件、ai-service 的 UPLOAD_DIR/PROCESSED_DIR 副本、chromadb collection。**chromadb 必须经 `PersistentClient.delete_collection` 删除**，直接删目录会损坏 sqlite 索引（见 `ai-service/app/api/files.py`）。ai-service 侧删除不清 `ai:cache:*` 孤儿缓存键（fileId 不复用 + 短 TTL，无正确性问题）。
6. **错误格式统一**：跨端统一 `{ error: { message } }`。backend 错误类 → HTTP 映射：Validation→400、NotFound→404、Conflict→409、AI 不可用→502、AI 超时→504、PostgreSQL 不可用→503（见 `utils/errors.ts`）；ai-service 侧各接口自行把 `ValueError`→400、`RuntimeError`→502。限流拒绝为 429 + `Retry-After`。前端拦截器只认该格式的 `message`。
7. **中文文件名下载**：必须同时给 `filename*`（RFC 5987 编码）与去非 ASCII 的 ASCII 兜底名，否则 Node HTTP 头直接抛错（历史 500 根因，见 `routes/download.routes.ts`）。
8. **Word 中文字体**：python-docx 设置中文字体必须同时设 `w:eastAsia`，否则中文不生效（见 `core/generator.py` 的 `_style_run`）。
9. **LLM 配置：环境变量为默认值，设置页覆盖**。embedding/OCR 等非 LLM 配置仍全部走 env（`ai-service/app/config.py`，新配置项要同步 `.env.example`）。LLM（api_key/base_url/model）在 env 之上还有一层动态设置：前端「模型设置」页写入 PostgreSQL `settings` 表 key='llm'（backend 独占写、ai-service 经 `llm/config_store.py` 直读同一行，3s TTL 缓存 + 30s 故障短路，fail-open 回落 env；行键镜像常量在 `settings.keys.ts` ↔ `config_store.py`，**勿单侧修改**），换模型在页面切换即时生效（无需重启）。新增 LLM 调用点必须经 `LLMClient`（slot='main'/'outline'）构造，不得绕过直接读 env。
10. **大模型惰性加载**：OCR 引擎、embedding 模型均为首次使用时加载（首次请求慢是预期），禁止在 import 时加载，否则启动即卡死。
11. **超时与重试**：backend→ai-service 统一 120s（AbortController→504）；LLMClient 内部 120s + 重试 2 次。新增长耗时功能要重新评估这两处超时。
12. **上传幂等**：`fileService.save` 按 sha256 + 原文件名去重，重复提交返回既有记录；multer 用内存存储（buffer 在异步闭包中仍可读），20MB 上限在 `env.maxFileSizeMb`。
13. **后台解析是 fire-and-forget**：进程重启后任务丢失，靠启动时 `recoverStaleParsingTasks` 兜底——只扫 `files` 表中 `status='parsing' AND updated_at < 超时线` 的记录（部分索引 `files_parsing_idx`，O(在途) 而非 O(全量)），超时置 failed。若新功能复用该模式，进入/离开 parsing 必须经 `fileService.updateStatus`；否则演进为任务队列（见第 5 节方向 2）。
14. **CORS**：backend 放行来源在 `env.corsOrigins`（默认 localhost），上 VPS 需配置（见部署指南）。
15. **跨端字段命名映射**：ai-service 的 Pydantic 模型为 snake_case（`doc_title`/`section_count`），backend 对外契约为 camelCase（`docTitle`/`sectionCount`），字段名**必须在 `ai-client.service.ts` 边界做映射**——直接透传会 422（新增字段）或静默失效（可选字段被 Pydantic 忽略，历史 bug：outline 的 sectionCount 曾静默失效）。
16. **ai-service 缓存必须 fail-open**：LLM/检索缓存全部经 `core/cache.py`（Redis 挂掉只记日志 + 30s 短路，业务照常走原路径）。新增缓存点必须：key 用 cache.py 的 `llm_key/outline_key/search_key` 生成（digest 含生效模型的 model@base_url，设置页切模型自动失效）；异常/空结果不入缓存；「重新生成」类入口（如 `/ai/generate/section`）显式 `use_cache=False`。
17. **网关限流是保护措施，不能成为单点**：限流中间件 fail-open（Redis 不可用直接放行）；必须挂在 multer 之前（429 时 `req.resume()` 排空请求体）；GET 轮询接口（`/api/files/:fileId`，前端 2s 轮询）**不得**挂限流；nginx 反代后必须开 `TRUST_PROXY`，否则全站共享代理 IP 一个桶。
18. **SSE 落库需要「转发 + 旁路解析」同时进行**：问答流不能像以前那样裸 pipe——`qa.service` 解析 token/sources/done，done 后事务写 `conversations`/`conversation_messages`；客户端 `res.close` 时 destroy 源流以取消上游 reader；新会话未完成要清理空会话。**自定义响应头（`X-Source-FileIds` / `X-Conversation-Id`）必须加入 CORS `exposedHeaders`**，否则跨域前端 fetch 读不到（既有引用映射也曾受此影响）。

### PostgreSQL 表速查（事实源）

| 表 | 说明 |
| --- | --- |
| `files` | FileMeta 一行一文件（file_id 为 text PK——生成类记录存 ai-service 的 32 位 hex id，勿改 uuid 列）；索引：`files_created_at_idx`（列表倒序）、`files_parsing_idx`（部分索引，启动恢复只扫它）、`files_dedup_idx`（**非唯一**部分索引，上传幂等去重）；`user_id` 为二期用户系统预留列 |
| `conversations` | 问答会话：title、file_ids（JSONB；**null = 全库**，数组为对外 fileId）、user_id（预留）；按 updated_at 倒序列表 |
| `conversation_messages` | 会话消息：role（user/assistant，CHECK）、content、sources（assistant 专属，fileId 已映射为对外 fileId）；FK ON DELETE CASCADE；索引 (conversation_id, created_at) |
| `settings` | key='llm' 一行存 LLM 设置 JSON（供应商列表 + 主/大纲槽位）；backend 独占写（行键收口 `services/settings.keys.ts`），ai-service 直读（镜像见 `app/llm/config_store.py`） |
| `app_meta` | 应用元信息：Redis→PG 迁移标记（`redis_files_imported` / `redis_settings_imported`） |

### Redis 键空间速查（仅缓存与限流）

| 键 | 库 | 类型 | 说明 |
| --- | --- | --- | --- |
| `backend:ratelimit:{bucket}:{ip}:{window}` | 0 | string | 限流计数（窗口内自动过期，fail-open） |
| `ai:cache:{kind}:{sha256}` | 1 | string | LLM 结果（summary/mindmap/topic-outline/section），TTL 24h |
| `ai:cache:search:{fileIds}:{sha256(question)}` | 1 | string | 检索结果 JSON，TTL 1h |

冻结旧键（元信息已迁 PG，仅回滚窗口期保留，稳定运行 1-2 周后可清理）：`backend:files:{fileId}`、`backend:files:index`、`backend:files:dedup`、`backend:files:parsing`、`backend:files:migrated`、`backend:files:pg-imported`、`backend:settings:llm`（键名注册表见 `services/file.keys.ts` / `settings.keys.ts`，迁移脚本 `redis-import.service.ts` 是唯一读者）。

运维注意：本地 `redis-cli` 查 ai-service 缓存要带 `-n 1`；清缓存 `redis-cli -n 1 FLUSHDB`（不影响限流计数）；备份事实源 = `pg_dump`（注意 dump 含明文 apiKey，需限制备份文件权限）；files.json 只是历史冷备份。

## 五、扩展方向与落点

按投入分级，每个方向给出三端改动点与主要风险。

### A. 短期（1-2 天级，复用既有链路）

| 方向 | 改动点 | 复杂度 | 主要风险 |
|------|--------|--------|---------|
| **Word→PDF 转换** | ai-service `core/converter.py` 加方法 + `api/convert.py` 加路由；backend `convert.service/routes` 加一条；frontend 加页面或 tab。完整流程见第 3 节 | 低 | 需要 LibreOffice（soffice）环境，Docker 镜像体积大增；排版保真度有限 |

## 六、高亮点功能专项（已立项）

> 以下均为已立项的亮点功能。实施时遵守第 2 节分层约定与第 4 节坑点清单（尤其双 fileId、错误格式、超时三处），落地后按第 7 节收尾清单同步文档。

### 6.1 页级引用 + 多文件知识库问答（已实施）

**目标效果**：

- 问答引用从「第 N 段」（对用户无意义）升级为「**文件名 · 第 X 页**」，点击徽标弹出预览并定位到对应页（面试叙事：RAG 引用可溯源）；
- 知识库支持**多选**：多个文件组成一个知识库，答案综合引用多个文件的相关片段（如「A 和 B 的区别」类问题）。

**共享底座（先做，一次到位，避免返工）**：

两项功能改的是同一批字段（块 metadata 与 sources 契约），必须合并实施：

1. **块 metadata 扩展两个字段**：`page`（块起始页页码）+ `filename`（来源文件名，`parse.py` 上传时已知）。`PageText.page_index` 一直在记录页码，只是 `Chunker.chunk` 分块时丢弃了；注意块缓冲会**跨页累积**，需在缓冲首行入缓冲时记录其页码。
2. **sources 契约一次到位**：`{ chunkIndex, page, fileId, filename, text }`，三端类型同步（backend types / ai-client 返回类型 / frontend QaResult）。
3. **历史数据迁移**：旧 collection 无 page/filename 元数据，需删除后重新上传解析，两者合并只迁一次；取不到时兜底 `null`（前端显示「未知页」）。

**A. 页级引用跳转**：

- `QAEngine.ask` 的 sources 增加 page/fileId/filename。
- 下载接口增加 `?inline=1` 预览模式（现有 attachment 头在 iframe 中会直接触发下载，无法内嵌预览）。
- 前端引用徽标按文件类型显示「第 X 页」/「第 X 段」，点击弹 `PdfPreview` 定位。

**B. 多文件知识库问答**：

- ai-service 新增 `ask_multi(file_ids, question, history)`：问题向量**只编码一次** → 逐 collection 检索（**每文档 top-3**）→ 合并按距离排序取整体 top 6-8 → 上下文按「来源：《文件名》」标注 → LLM 生成。同模型归一化向量，跨 collection 距离可直接比较。
- **per-doc cap 3 防单文档刷屏**；Prompt 加「若问题涉及多个文档的对比，请综合引用多个来源」指令（对比类问题关键）。
- backend 契约兼容 `fileIds?: string[]`（保留单 `fileId` 不破坏既有调用）：逐文件校验 parsed（409 报错**指名哪个文件**未解析）+ aiFileId 映射。
- 前端 KnowledgeBase 改多选（checkbox），QaPage 的 `activeFileId` 变 `activeFileIds: string[]`；知识库列表只含已解析文档，轮询只需盯**新上传的那个文件**（`useFileStatus` 不改）；某文档被删（404）→ 从选中集**剔除该项**，而非整场重置。

**分端改动明细**：

| 端 | 文件 | 改动 | 所属 |
|----|------|------|------|
| ai-service | `app/core/rag.py` | `Chunk` 加 page/filename；`Chunker.chunk` 记录缓冲起始页；`VectorStore.store` metadata 加两字段；`QAEngine.ask` sources 加 page/fileId/filename；新增 `ask_multi`（一次编码 + 逐 collection top-3 + 合并排序 + 来源标注 Prompt） | A+B |
| ai-service | `app/api/parse.py` | `build_and_store` 传入 filename 并存入 metadata | B |
| ai-service | `app/api/qa.py` | `QaRequest` 支持 `fileIds`，多文件时调用 `ask_multi` | B |
| backend | `src/types/index.ts` | `SourceChunk` 加 `page?`/`filename?`/`fileId`；`QaAskRequest` 加 `fileIds?: string[]` | A+B |
| backend | `src/services/ai-client.service.ts` | `qa()` 参数与返回类型同步（支持 fileIds） | A+B |
| backend | `src/services/qa.service.ts` | 循环校验每个 fileId parsed + aiFileId 映射，409 指名未解析文件 | B |
| backend | `src/routes/download.routes.ts` | 增加 `?inline=1` 预览模式：`Content-Type: application/pdf` + `Content-Disposition: inline`（现有 attachment 头在 iframe 中会直接触发下载） | A |

| frontend | `src/components/PdfPreview.tsx`（新） | Modal + `<embed src={downloadUrl(fileId) + '?inline=1#page=N'} />` | A |

**边界与坑**：

- **分块跨页**：块可能横跨多页，`page` 取起始页即可满足跳转定位；后续可扩展 start/end page。
- **docx 无真实页码**：`parse_docx` 的 page_index 实为段落序号，前端按文件类型显示「段」/「页」。
- **`#page=` 兼容性**：Chrome/Edge 内建 PDF 查看器支持 URL fragment 定位；Firefox/Safari 需换 PDF.js 精确渲染（v2：前端加 pdfjs-dist，按 page 渲染单页）。
- **单文档刷屏**：不设 per-doc cap，相似度最高的一篇会占满 top 5，其他文件永远引不到——cap 与合并排序是必做项。
- **对比类问题**：跨文档检索命中 ≠ 能对比，Prompt 多来源指令与 per-doc cap 是必要配套。
- **逐 collection 检索为串行**：文档数少（2-10 个）时毫秒级，无压力；未来到几十个再并行化。
- 扫描版 PDF 无文本层，本就没有检索块，与解析降级行为一致，无需特殊处理。

**验收**：上传带目录的 PDF → 提问 → 引用显示「文件名 · 第 X 页」→ 点击徽标弹窗定位到对应页；docx 显示「段」；多选 2-3 篇文档提问「A 和 B 的区别」→ 答案引用两个文件、徽标各自跳转；选中文件被删（404）→ 从选中集剔除、其余文档继续可问；旧文档（未重传）显示「未知页」不报错；`?inline=1` 在 iframe 内联渲染而非触发下载。

**实施记录（2026-08-23，已按本节计划落地）**。与计划的差异：

1. 改动文件补充：`backend/src/routes/qa.routes.ts` 也在改动之列（计划表格遗漏——`AskBody` 需透传 `fileIds`）。
2. 页码统一在 `Chunker.chunk` 入库时 `page_index + 1` 转 1-based（PDF `page.number` 与 docx 段序号均为 0-based），展示与 `#page=` 定位直接用，前端不换算。
3. backend 返回前把 `sources.fileId` 从 aiFileId **反向映射为对外 fileId**（计划只写了正向映射；前端拼下载地址需要对外 fileId）。
4. 块起始页按「行起始偏移表」逐行追踪（缓冲跨页累积且超长切分会丢掉前半段，仅记首行页码会失准）；切点落在行中间时用该行页码兜底。
5. 旧 collection 的 metadatas 可能为 `None`，统一 `(m or {}).get(...)` 兜底 null（否则 `m.get` 直接崩）。
6. 合并排序为稳定排序，距离平局时按传入 fileIds 顺序，行为确定。
7. 多文件合并取整体 top-8（计划 6-8 的上限）；每文档 top-3 不变。

### 6.2 文档 → 思维导图

**目标效果**：上传文档一键生成可缩放/折叠的脑图（markmap）。30 秒 demo：上传论文 → 结构化脑图，视觉冲击力远强于文字摘要。

**方案要点**：

1. **树来源两条路径**（`app/core/mindmap.py` 新建）：
   - `build_from_titles`：从向量库 chunk 的 title 元数据重建树（按 `" > "` 分割标题路径）。docx 已有 H1/H2/H3 标记，开箱即用。
   - `build_via_llm`：LLM 从前 N 块生成 markdown 提纲。**注意：`parse_pdf` 目前不带标题标记**，PDF 文档 titles 路径为空，`mode=auto` 时回退此路径（约 30-60s，仍在 120s 超时内）。
   - 可选增强（后续）：PDF 标题识别启发式（fitz `get_text("dict")` 按字号/加粗判标题行），让 PDF 也能走 titles 路径。
2. **输出契约用 markdown 提纲字符串**（markmap 原生输入格式），不做 JSON 树，前后端都省一层转换。若 LLM 输出格式不稳，备选方案是让 LLM 返回 JSON 树再转 markdown。
3. 新接口 `POST /ai/mindmap {fileId, mode?: 'auto'|'titles'|'llm'}` → `{ markdown }`；backend 沿 qa/summary 链路转发（parsed 校验 + aiFileId 映射）。

**分端改动明细**：

| 端 | 文件 | 改动 |
|----|------|------|
| ai-service | `app/core/rag.py` | `VectorStore` 增加 `get_chunks(file_id)`（include metadatas，返回带 title 的块，供重建树） |
| ai-service | `app/core/mindmap.py`（新） | 两条构建路径 + auto 调度 |
| ai-service | `app/api/mindmap.py`（新） | `POST /ai/mindmap`：校验 + 错误映射（ValueError→400 / RuntimeError→502） |
| ai-service | `app/main.py` | 注册 mindmap router |
| backend | `src/services/mindmap.service.ts`（新） | 复用 qaService 的 parsed 校验模式 → `aiClient.mindmap` |
| backend | `src/routes/mindmap.routes.ts`（新）+ `app.ts` | `POST /api/mindmap` |
| backend | `src/services/ai-client.service.ts`、`src/types/index.ts` | `mindmap()` 方法 + `MindmapResponse { markdown }` |
| frontend | `package.json` | 新增 `markmap-lib`、`markmap-view` 依赖 |
| frontend | `src/api/index.ts` | `mindmap(fileId)` |
| frontend | `src/pages/MindmapPage.tsx`（新） | 整体照抄 SummaryPage 流程：FileUpload → ParseStatus → 生成按钮 → markmap 渲染 |
| frontend | `src/App.tsx`、`src/pages/Home.tsx` | 路由 `/mindmap` + 首页入口卡片 |

**边界与坑**：

- **PDF 无标题结构（现状）**：auto 模式回退 LLM 生成，首次体验慢（LLM 调用）；LLM 路径只喂前 10-15 块控制 token 与时延。
- 标题路径分隔符 `" > "` 与标题原文冲突概率极低，若出现需换分隔符或转义（Chunker 的 `title_path` 拼接处）。
- LLM 输出的 markdown 可能不规范（缩进错乱），markmap-lib 转换失败需容错提示重试；必要时后端做一次正则清洗。
- markmap 渲染为 SVG 交互（缩放/折叠），中文无碍；导出 PNG 是 v2 可选项（需额外截图库）。
- 未配置 LLM_API_KEY 时 docx 的 titles 模式仍可用，llm 模式报错与既有 LLM 错误一致。

**验收**：上传带多级标题的 docx → 生成脑图，层级与标题一致、可缩放折叠；上传 PDF → auto 回退 LLM 生成脑图；错误路径（未解析 409 / 文档已删除 404）提示正常。
