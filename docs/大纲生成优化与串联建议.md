# 大纲生成 · 优化与功能串联建议

> 面向后续迭代：大纲→Word 生成功能的**优化点**与**跨功能串联方向**。
> 基线：2026-08，大纲生成已跑通（逐节 LLM 生成 + python-docx 公文样式渲染），
> 但它是四大功能中**最孤立**的一个——与问答/摘要/思维导图/知识库零交互。
> 配套文档：[功能拓展指南](功能拓展指南.md)、规格说明书（仓库根目录）。

---

## 一、现状与问题盘点

| 维度 | 现状 | 问题 |
|------|------|------|
| 大纲来源 | 用户在文本框里逐行手敲（`GeneratePage.tsx`） | 冷启动难：用户要自己先想好大纲，功能价值减半 |
| 生成方式 | 全量同步生成：逐节串行调 LLM，一个接口从头等到尾 | 节数一多（>6 节）可能撞 120s 超时；前端只有一个 Spin，无进度反馈 |
| 结果反馈 | 只有下载按钮（`ResultDownload`），文件名固定为「生成文档.docx」 | 用户必须下载才知道质量；不满意就要整个重来（重新花钱花时间） |
| 大纲结构 | 扁平 `string[]`，无层级 | 无法表达 H1/H2/H3 层级；与思维导图/分块的标题层级能力不匹配 |
| 与知识库 | 无交互 | 参考文档的大纲提不出来；生成的文档也进不了知识库 |

核心结论：**大纲生成具备成为"文档创作中枢"的潜力——上游接参考文档/脑图/主题，下游回收到知识库**，但目前只有"手输大纲 → 下载 Word"一条窄路。

---

## 二、功能串联全景（目标形态）

```
                    ┌─────────────── 主题（一句话）──────────────┐
                    │  LLM 自动生成大纲（复用思维导图 llm 路径）      │
                    ▼                                            │
 上传文档 → 解析入库 → 思维导图（titles 提取大纲） ──► 大纲编辑 ──► 逐节生成 Word
    │          │                                    ▲         │
    │          └── 问答 / 摘要 / 多文档问答           │         │
    │                                               │ 单节重生成 │
    └──── 生成文档一键回收进知识库（问答/摘要/脑图） ◄──── 在线预览 ◄──┘
```

一句话叙事：**「上传参考文档 → 一键提取大纲 → 扩写成新文档 → 新文档入知识库继续问答」**，整个平台形成一个"读 → 思 → 写 → 再读"的闭环。面试叙事价值：从单点工具升级为文档工作流。

## 三、串联方向（按优先级）

### 3.1 参考文档 → 提取大纲 → 生成新文档（P0，核心闭环）✅ 已实施 2026-09-02

**目标效果**：上传一篇文档（论文/报告），一键提取其结构大纲，扩写/改写出一篇新 Word。场景：参考范文改写、报告模板套用。

**实现要点**：

- **能力已全部存在，只差一根管子**：
  - `core/mindmap.py` 的 `build_from_titles`（从向量库标题元数据重建树，docx 开箱即用）与 `MindmapLLM.outline`（LLM 生成 markdown 提纲，PDF 适用）输出就是 markdown 大纲；
  - `core/generator.py` 的 `generate_document` 只吃 `outline: list[str]`。
- 前端：GeneratePage 增加「从知识库导入大纲」入口 → 选已解析文档 → 调 `/api/qa/mindmap` → markdown 的 `#` 行解析为大纲列表（带层级，见 4.3）→ 填入可编辑区域。
- 后端：**无需新接口**，前端直接复用 `qaMindmap(fileId)`（`api/index.ts` 已有）。
- 后续可选：生成时把参考文档摘要注入 Prompt（"参考原文风格与要点，但不照抄"），改写质量更高。

**风险与坑**：

- PDF 的 titles 路径为空（auto 会回退 LLM，30-60s），用户等待期间要有明确状态提示；
- 从参考文档生成时注意 Prompt 约束"不得照抄原文"，规避查重/抄袭问题；
- markdown → outline 解析要容错 LLM 输出不规范（复用 `MindmapLLM._strip_fence` 思路）。

### 3.2 主题 → LLM 自动生成大纲（P0，零起点创作）

**目标效果**：用户只输入"写一份《XX 项目立项报告》"，LLM 自动给出 3-5 级大纲，用户增删改后点生成。解决手敲大纲的冷启动问题。

**实现要点**：

- 新接口 `POST /ai/outline`：`{ topic, sectionCount?: 5, style?: '报告'|'论文'|'方案' }` → `{ markdown }`；
- Prompt 直接改造 `MindmapLLM.PROMPT_TEMPLATE`（"根据主题列出大纲，而非阅读内容"），核心逻辑复用；
- 前端 GeneratePage 加「AI 帮我想大纲」按钮 + 主题输入框，返回结果填入大纲编辑器；
- 若大纲与层级结构（4.3）一起做，一次到位，避免返工。

**风险与坑**：LLM 输出层级/条数不稳定 → 前端解析失败时降级为"手动编辑"；Prompt 要锁死输出格式（只输出 markdown 大纲）。

### 3.3 思维导图 → 一键转大纲生成文档（P0 后半段，联动点睛）✅ 已实施 2026-09-02

**目标效果**：摘要页生成思维导图后，用户觉得结构不错 → 点击「用此大纲生成文档」→ 跳转生成页，大纲已预填，直接生成。脑图从"看完就完"变成创作起点。

**实现要点**：

- 前端：`SummaryPage.tsx` 脑图卡片加按钮，`navigate('/generate', { state: { title, outline } })`；GeneratePage 用 `useLocation` 读取 state 预填（纯前端改动，零后端成本）；
- 与 3.1 合并叙事：脑图按钮可同时提供「用大纲生成」两种来源（参考文档大纲 / LLM 提纲）。

### 3.4 生成文档一键回收进知识库（P1，闭环后半段）

**目标效果**：生成的 Word 一键「加入知识库」→ 走既有解析链路 → 可对生成的文档继续问答/摘要/脑图。让生成物变成可查询的知识资产。

**实现要点**：

- 生成结果已落在共享 `PROCESSED_DIR`（uuid.docx），backend 已登记 `processedPath`；
- 新增「加入知识库」按钮 → backend 新接口 `POST /api/generate/:fileId/import`：从 processedPath 读文件 → 复用 `parseInBackground` 同款逻辑调 `/ai/parse`（`upload.routes.ts` 的解析链可提取复用，注意它吃 multer file，需要适配为按路径读 buffer）；
- ai-service 侧无需改动（parse 接口只吃 multipart，转发即可）。

**风险与坑**：解析任务复用 fire-and-forget 模式，注意 files.json 上该生成记录状态从 `converted` 迁移到 `parsing → parsed`（`updateStatus` 已支持）；若用户删除生成文档，走既有删除联动即可。

### 3.5 多文档综合大纲（P2，进阶）

**目标效果**：多选 2-3 篇参考文档，生成一份综合大纲（如"把三份竞品报告综合成一份调研报告"），一键转生成 Word。

**可行性**：能力几乎现成——多选知识库（`KnowledgeBase.tsx` 多选）与多文件检索（`rag.py` 的 `_retrieve_multi`：问题向量单次编码、逐 collection top-3）均已跑通，缺的只是"多文件 → 提纲"这一步。

**两条路径（与单文档 mindmap 同构，auto 调度）**：

1. **titles 合并（结构并集，推荐首选）**：对每个 file_id 调 `build_from_titles`，每棵树的根是文件名（`mindmap.py` 已有 `# {filename or '文档大纲'}` 单根保证），多棵树平级拼成「文档A > 章节…」「文档B > 章节…」的综合树 → 一份**带来源标注**的结构化大纲。快（毫秒级）、确定性强，且天然保留"哪些章节来自哪篇文档"的出处。
2. **llm 综合（主题归并）**：各文档取前 N 块 + 「来源：《文件名》」标注（复用 `ask_multi` 的标注模式）→ Prompt 指令"归并相同主题章节、保留各文档独有章节、观点冲突处并列标注" → LLM 生成融合大纲。慢（30-60s+），但能把三份文档里重复的「市场分析」归并为一章。

**同名章节问题**：titles 路径下三份报告各自的「市场分析」会并存（挂在各自文档名下，不冲突，可读）；llm 路径下由 Prompt 决定归并——两种输出语义不同，前端展示时可注明当前模式。

**接口与契约**：

- ai-service：`core/mindmap.py` 新增 `generate_multi_markdown(file_ids)`（auto 调度：全员有标题结构走 titles 合并，否则 llm 兜底）；`api/mindmap.py` 请求体加 `fileIds?: string[]`（与 `fileId` 互斥，与问答接口同款兼容写法）；
- backend：`qaService.mindmap` 循环校验每个 fileId 已解析（复用 `requireParsed`）+ aiFileId 映射——与 `qa.service.ts` 的 `askStream` 校验逻辑完全同款；
- frontend：`SummaryPage` 脑图生成支持知识库多选（多选能力已存在）；生成后与 3.3 一样一键跳转生成页。

**风险与坑**：

- token 上限：每文档只取前 N 块（如 10 块），否则 llm 路径随文档数爆上下文；
- 章节重复与冲突：titles 路径输出会含同名章节，生成 Word 前用户需在编辑器里删并——建议前端编辑器对"同名章节"做高亮提示；
- 部分文档有标题、部分没有：auto 调度按"至少一个文档无标题结构 → llm 综合"兜底，titles 合并只适用于全员有标题的场景。

## 四、生成体验优化（不依赖串联）

### 4.1 逐节流式进度（P0，最紧迫的工程优化）✅ 已实施 2026-09-02

**问题**：全量同步生成，`ContentGenerator.generate` 逐节串行调 LLM。6 节 × 每节 15-30s ≈ 90-180s，随时撞 backend→ai-service 的 120s 超时（`ai-client.service.ts` 的 `AI_TIMEOUT_MS`），用户只看一个 Spin 干等。

**方案**：把 `/ai/generate` 改成 SSE（复用问答的成熟链路）：

```
data: {"type":"section_start","index":1,"title":"项目背景"}
data: {"type":"section_done","index":1,"preview":"…该节前 200 字…"}
data: {"type":"done","fileId":"…"}
或中途失败：data: {"type":"error","message":"第 3 节生成失败"}
```

- ai-service：`api/generate.py` 改 `StreamingResponse`（照抄 `api/qa.py` 的 `_sse` 包装）；`core/generator.py` 增加 `generate_document_stream` 生成器；
- backend：`qa.routes.ts` 的 SSE 透传模式照搬；
- 前端：`qaAskStream` 的帧解析逻辑照搬，进度条按"节数"推进，每节完成展示节标题 + 预览片段（**预览见 4.2，一次做完**）；
- 超时体系重新评估：SSE 流式下 120s 超时对单节仍适用（每节一个 LLM 调用），整体不再受限。

### 4.2 在线预览 + 单节重生成（P1，省钱的利器）✅ 已实施 2026-09-02（含增量生成、阅读模式、模型分层）

**目标效果**：生成完成后**页内预览全文**（不用下载），某节不满意**只重生成那一节**，而不是整篇重来。

**实现要点**：

- SSE 每节事件带该节全文 → 前端以分节卡片渲染预览（标题 + 段落 + 要点，可复用 `react-markdown` 渲染为 HTML 预览而非真实排版）；
- 单节重生成：新接口 `POST /ai/generate/section`：`{ docTitle, sectionTitle, previousSections?: string[], requirements? }` → 复用 `ContentGenerator._ask_llm` + `_parse_section`；前端替换对应卡片；
- 全部满意后：`POST /ai/generate/assemble`：`{ title, sections: [{title, paragraphs, bullets}] }` → 只做 `DocxRenderer.render` 渲染（不调 LLM，秒出），这是「内容生成与格式渲染分离」架构的红利，面试可讲。

**风险与坑**：节内容在前后端间来回传，注意 20MB/120s 之外的 payload 大小限制（Express `express.json` 默认 100kb！需要 `express.json({ limit })` 调大）；`assemble` 接口要防御脏数据（字段缺失/超长）。

### 4.3 层级大纲（P1，与串联方向互为基础）

**目标效果**：大纲支持 H1/H2/H3 层级，Word 里对应三级标题（黑体 14/13/12pt，文档大标题 16pt），生成文档不再是一级标题平铺。

**实现要点**：

- 契约升级：`outline: string[]` → `outline: { level: 1|2|3, title: string }[]` 或沿用 markdown `#` 语法（与思维导图/脑图输出天然同构，**推荐 markdown**）；
- `DocxRenderer.render` 按 level 渲染（`_add_heading` 已参数化 size，扩展成三级即可）；
- 分块侧 `Chunker._parse_heading` 已支持 H1/H2/H3——层级大纲生成的内容，未来回收入知识库时标题结构自动成立（与 3.4 串联）；
- 向后兼容：backend 校验时 `string[]` 仍接受（视为 level=1）。

### 4.4 章节间一致性（P1，质量优化）

**问题**：现在每节独立生成，互不知晓——各节可能重复论述同一内容，或口径互相矛盾（前面说"预计 3 个月"，后面说"预计 2 个月"）。

**方案**：链式上下文——生成第 N 节时，把前几节的**要点摘要**（每节取前 2 句，或单独轻量 LLM 摘要）注入 Prompt："前文要点：……请避免重复并保持口径一致"。改动集中在 `ContentGenerator.generate` 循环内，接口契约不变。

**风险与坑**：token 随节数线性增长（长文档末尾几节上下文变长）；前文摘要的额外 LLM 调用会拉长总耗时——建议仅取各节标题 + 首段，不做额外调用。

### 4.5 风格/篇幅参数与大纲模板库（P2）

- 生成参数：`{ style: '公文'|'报告'|'论文', length: '简短'|'标准'|'详细' }` → Prompt 参数化（同摘要 options 方向，见功能拓展指南第 5 节 A）；
- 模板库：预设大纲（开题报告/项目方案/述职报告/活动策划），前端常量内置即可，选中即填入编辑器；与 3.2 的 LLM 生成大纲互为补充（模板保底、LLM 定制）。

### 4.6 目录与页码（P2，公文感）

- python-docx 插入 TOC 域代码（`w:fldSimple` + TOC 指令），用户打开 Word 按 F9 刷新目录；
- 页脚页码 + 文档标题页眉，提升"真能交差"的观感。

### 4.7 小修快补（P1，半小时级）

| 问题 | 位置 | 修法 |
|------|------|------|
| 下载文件名永远是「生成文档.docx」，不体现标题 | `generate.service.ts` 的 `RESULT_FILENAME` 常量 | `saveGenerated` 传 `${title}.docx`（注意中文文件名走既有 RFC 5987 逻辑，已兜底） |
| ai-service 返回的 `fileId` 与落盘文件名是两个 uuid | `api/generate.py` 末尾重新 `uuid.uuid4()` | 直接用 `core/generator.py` 生成时的 uuid（返回值已带 filename），删掉重复生成 |
| 第 3 节失败 → 前 2 节成果全丢 | `ContentGenerator.generate` | 断点容错：失败时抛出**含已完成节**的异常信息，或前端先重试单节（4.2 落地后自然缓解） |
| `express.json` 默认 100kb 限制 | `app.ts` | 4.2 的 assemble 接口如传全文，必须调大 `limit` |

## 六、实施顺序建议

```
第一期（串联主线，面试叙事成型）：
  4.1 流式进度 ──► 3.1 参考文档导入大纲 ──► 3.3 脑图一键转生成
第二期（体验闭环）：
  4.3 层级大纲 ──► 4.2 在线预览 + 单节重生成 ──► 3.4 生成文档入知识库
第三期（打磨）：
  3.2 主题生成大纲、4.4 章节一致性、4.7 小修 ──► 4.5/4.6 模板与目录
远期：
  3.5 多文档综合大纲
```

优先级逻辑：**第一期先打通"参考文档 → 大纲 → 新文档"的叙事主线**（改动小、复用多、面试最好讲）；第二期补体验闭环；第三期打磨质量。每一期落地后按功能拓展指南第 7 节收尾清单同步文档。

## 七、实施记录（2026-09-02，已落地：3.2 + 4.3 + 4.7 部分）

> 实施前按"实用主义"重新排序：先解决"用户想不出大纲"（3.2），再解决"生成物质量没底"（4.2），最后补闭环叙事。本批落地 3.2（主题生成大纲）+ 4.3（层级大纲）+ 4.7 前两项小修。与计划的差异：

1. **outline 接口并入 generate.py**：`POST /ai/generate/outline`（而非计划中的独立 `/ai/outline`），backend 对应 `POST /api/generate/outline`，前端 `generateOutline()`。
