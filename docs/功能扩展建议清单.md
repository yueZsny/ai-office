### 1.2 可直接复用的底座

这些是后续扩展的「顺风车」，新功能优先复用，不要另起炉灶：

- **SSE 全链路**：`app/api/sse.py`、`generate.service.ts` 的 `sseEvents`、前端 `fetch` 帧解析——任何长耗时功能都可套用。
- **内容与渲染分离**：`SectionContent { title, level, paragraphs, bullets }` + `assemble_document`，可以在不调 LLM 的情况下快速产出 Word。
- **块级 metadata**：`title / page / filename / index` 已入库，适合做搜索、引用、差异、图谱类功能。
- **LLM 槽位机制**：`LLMClient(slot=...)` + 设置表，新增任务类型（摘要、对比、提炼）可以低成本独立配模型。
- **缓存键收口**：`cache.py` 的 `llm_key / outline_key / search_key` 已把生效模型纳入 digest。
- **文件状态机**：`uploaded → parsing → parsed/converted/failed`，新增任务类型可扩展，不必重造轮子。
- **双 fileId 映射**：对外 `fileId` 与 `aiFileId` 的转发/反向映射已有成熟写法（`qa.service.ts`）。

### 1.3 真正值得优先补齐的短板

按「用户可感知程度 ÷ 改动成本」排序：

| # | 短板 | 代码证据 | 用户感受 |
|---|------|---------|---------|
| 1 | **扫描版 PDF 解析“成功”但完全不可用** | `parse_pdf` 只取文本层；空文本仍会入库并置 `parsed`，直到问答才报「尚未解析」 | 上传扫描合同/论文 → 问答/摘要全部失败，且不知道原因 |

## 三、P0 速赢详解

### P0-1 扫描 PDF OCR 兜底

**问题**：`parse_pdf` 只用 `page.get_text()` 取文本层；扫描件每页为空字符串，`build_and_store` 仍会「成功」入库一个空 collection。前端看到 `parsed`，提问却报「该文件尚未解析」，摘要也报错。

**方案**：

1. `ai-service/app/core/parser.py` 的 `parse_pdf` 逐页判断：文本长度低于阈值（如 20 字符）时，`page.get_pixmap(dpi=200)` 渲染为临时 PNG，复用现有 `_get_ocr_engine()` 识别后合并文本。
2. 增加配置：`PDF_OCR_MIN_CHARS`（触发阈值）、`PDF_OCR_MAX_PAGES`（防超时，默认 30）、`PDF_OCR_DPI`（默认 200）。
3. `ParseResult` 增加 `ocr_pages` 计数，`/ai/parse` 响应带上它；backend 可据此在 `errorMessage` 或未来任务详情里提示「已 OCR N 页」。
4. 如果一页 OCR 也识别不出内容，**显式报错**而不是静默成功：`ValueError("文档无可提取文本（扫描件且 OCR 失败）")`，让状态落到 `failed`，用户知道该换文件。

**风险**：

- OCR 是 CPU 密集型，30 页可能在 120s backend 超时附近；先用页数上限 + 低 DPI 控制，长期与 P1-4 任务队列一起解决。
- `parse_ocr` 当前吞掉所有异常并返回空结果，扫描 PDF 路径应至少记录日志、区分「无文字层」与「OCR 失败」。

**验收**：上传 3 页扫描 PDF → 状态 `parsed` → 摘要/问答有内容；引用页码正确；超过上限的页数在 UI 有提示。

**预估**：0.5-1 人日。

### P0-2 知识库全局语义搜索 / 免选择问答

**现状**：问答必须先勾选文档；知识库列表没有搜索，只能肉眼找文件名。

**方案**：

1. ai-service 新增 `POST /ai/search`：入参 `{ fileIds?, query, topK? }`；复用 `_retrieve_multi` 的「问题向量编码一次 + 逐 collection 检索」，返回 `{ fileId, filename, page, chunkIndex, text, score }`，**不调 LLM**，毫秒级。
2. backend 新增 `POST /api/files/search`：`fileIds` 省略时取全部 `parsed` 文档；把 `aiFileId` 映射回对外 `fileId`。文档数多时限制参与检索的文档数（如最近 50 篇）并在响应中返回 `truncated`。
3. 前端知识库顶部加搜索框：输入即搜（防抖 300ms），结果按文档分组展示命中片段，点击「定位」打开 PDF 预览，「追问」把该文档加入选中集并跳转问答。
4. **免选择问答**：问答请求允许不传 `fileIds`，backend 自动解析为「全部已解析文档」，Prompt 沿用多文件模板。设置文档数上限并在 UI 明示范围。

**风险**：

- 逐 collection 串行检索在几十个文档时仍是毫秒级，但上百个会变慢；届时引入文档索引表或并行检索（P2-8）。
- 「全部文档」语义在未来多用户下会越权，需等 P2-1 鉴权落地；当前内网单用户可先做。

**验收**：不勾选任何文档直接提问 → 答案引用多篇；搜索框输入关键词/自然语言 → 2s 内出结果并可定位。

**预估**：1-2 人日。

### P0-3 上传格式扩展（txt/md/图片入口）

**现状**：`backend/src/utils/file.utils.ts` 的 `ALLOWED_EXTENSIONS` 只有 `.pdf/.docx`；ai-service 的 `parse_file` 已支持图片 OCR，但上传入口没开。

**方案**：

1. 最小闭环：`ALLOWED_EXTENSIONS` 增加 `.txt/.md/.jpg/.jpeg/.png/.bmp`，前端 `FileUpload` 的 `accept` 同步。
2. `parser.py` 增加纯文本分支：`.txt/.md` 直接读取（`utf-8` 优先、`gb18030` 兜底），按段落/空行拆成 `PageText`；Markdown 可用标题行生成 `H1:/H2:` 前缀，直接复用现有分块与 `titles` 脑图路径。
3. `FileType` 联合类型、DB 的 `files_type_check` 约束、`resolveFileType` 三处同步加 `txt` / `md`。
4. 前端上传文案与 OCR 等待提示同步调整。

**后续可选**：`.doc`（LibreOffice 转换后解析）、`.pptx`（python-pptx 逐页取文本）、`.xlsx`（openpyxl 逐表转文本）、URL 导入（P1-8）。

**风险**：图片 OCR 首次加载引擎慢（10s+），需保留现有 120s 超时并提示「首次识别较慢」；`.txt` 编码判断避免乱码。

**验收**：上传 `.md` 笔记 → 问答/摘要/脑图正常，脑图能走 titles 路径；上传截图 → OCR 后可问答。

**预估**：0.5 人日（txt/md/图片）；doc/pptx/xlsx 另加 2-3 人日。

### P0-4 问答会话持久化

**现状**：`QaPage` 的对话只在 React state，刷新即丢；`history` 每次由前端全量回传。

**方案**（新增两张 PG 表，走 Drizzle 迁移）：

```text
conversations: id, title, file_ids jsonb, created_at, updated_at, user_id(预留)
messages:      id, conversation_id FK, role, content, sources jsonb, created_at
```

1. backend 新增 `/api/conversations` 的增删改查 + 消息列表；`POST /api/qa/ask` 增加可选 `conversationId`。
2. **SSE 存档**：当前 `qa.routes.ts` 是原样 pipe，无法在结束后落库。参照 `generate.service.ts` 的 `sseEvents`，改为「解析帧 + 转发 + 累积 token/sources」，流结束把 assistant 消息写入 `messages`；响应头返回 `X-Conversation-Id`（新建会话时）。
3. 历史从服务端读取最近 N 轮（如 10 轮）再传给 ai-service，前端不再维护完整 history。
4. 前端左侧知识库上方加会话列表：新建、重命名、删除、回看；点击历史消息可重新打开当时引用的文档状态（文件已删则标记）。

**风险**：

- backend 改「帧解析代理」后，任何一帧解析异常都要保证连接收尾与错误格式统一；参考 generate 的容错写法。
- 消息表会增长，加 `created_at` 索引与按会话分页；sources 以 JSONB 存原文片段，注意单条大小。
- 多用户前，会话与文件一样是全站可见；P2-1 时补 `user_id` 过滤。

**验收**：提问后刷新页面 → 会话与引用完整恢复；连续追问仍带上下文；删除会话不影响文件。

**预估**：2-3 人日。

### P0-5 摘要选项 + 结果导出

> ✅ 已落地（2026-10-24）：实际实现为覆盖上限 40 块的 map-reduce + 均匀抽样，并返回覆盖元数据；详见「九、实施记录」。

**方案**：

1. `POST /ai/summary` 增加可选参数：`length`（简短 150 字 / 标准 300-500 字 / 详细 800+）、`style`（段落 / 要点列表）、`focus`（可选主题，如「只总结实验部分」）。
2. 长文档改为 **map-reduce**：按每 10 块分组先各自摘要，再合并生成总摘要；块数 ≤10 时保持单次调用。缓存 key 必须把新参数纳入（`llm_key("summary", content, length, style, focus)`），否则不同选项会互相污染。
3. 导出：
   - Markdown / 纯文本：前端 `Blob` 直接下载，零后端成本。
   - Word：复用 `POST /api/generate/assemble`，把摘要包成单节（`title: "摘要", paragraphs: [summary]`），无需新接口。
4. 可选：摘要也走 SSE 流式（复用 `app/api/sse.py`），减少长文档等待焦虑。

**风险**：详细摘要的 token 成本上升，需在 UI 标明；map-reduce 结果与单次摘要口径不同，缓存 key 与 Prompt 必须区分。

**验收**：同一长文档切换「简短/详细」得到不同长度结果；导出 Word 可正常打开；重复请求命中缓存。

**预估**：1-2 人日。

### P0-6 Docx 在线预览

**方案（推荐 A）**：

- 前端引入 `docx-preview`（或 `mammoth`）：用 `fetch(downloadUrl)` 取 Blob，在 Modal 中渲染生成的 `.docx`。无需后端与 Docker 改动，适合「分节工作台生成物」「PDF→Word 转换物」的快速验收。
- 在 GeneratePage 的「下载 Word」旁加「预览」；ConvertPage 结果卡片加「预览」。

**方案 B（高保真，后续）**：

- ai-service 用 LibreOffice headless 将 docx → PDF，写入 `PROCESSED_DIR`（带缓存），复用现有 `?inline=1` 预览。优点是与 Word 排版一致；缺点是镜像增大约 300-500MB、首次转换慢——适合与 P1-3 的「导出 PDF」一起做。

**风险**：`docx-preview` 对复杂版式（表格、页眉页脚、分页）还原有限，要提前明确「预览仅供参考」；中文文件名走既有 RFC 5987 逻辑，无需改。

**验收**：生成文档与转换结果均可在页面内预览，无需下载。

**预估**：1-2 人日（方案 A）。

## 四、P1 重点

### P1-1 文档对比（A vs B）

**价值**：求职/办公场景的高频需求（两版合同、竞品报告、方案修订）。现有「多文档问答」只能问，不能结构化对比。

**方案**：

- ai-service 新增 `POST /ai/compare { fileIds: [a, b], aspect? }`：每篇文档按 aspect 检索 top-N 块（或短文档取全量），Prompt 输出固定 Markdown 结构：
  - 结论速览
  - 对比表（维度 | A | B）
  - 相同点 / 差异点 / 冲突点
  - 引用来源（文件名 + 页）
- 复用 `search_key` 缓存，key 含 fileIds 与 aspect；输出 Markdown 直接渲染，引用来复用现有 sources 事件结构。
- 前端新增 `/compare` 页面：从知识库多选 2 篇 → 选择对比维度（自动/自定义）→ 结果 + 可复制/导出 Word。
- 与 P1-6 综合摘要共享「多文档取块 + 来源标注」基础能力，建议一起设计。

**风险**：token 上限与两文档篇幅失衡；对比结论需要「只能基于材料」的严格 Prompt，避免模型凭常识补全；每篇文档要标注来源，否则无法核验。

**预估**：3-5 人日。

### P1-2 场景化提炼（学习卡 / 测验 / 会议纪要 / 待办）

**价值**：当前四大功能偏「通用文档处理」，加上场景模板后更贴近目标用户（学生 + 白领），也更容易形成演示亮点。

**统一能力**：`POST /ai/extract { fileIds, kind, options? } → JSON`，`kind` 取：

| kind | 输出 | 面向 |
|------|------|------|
| `key-points` | 分层要点 + 原文出处 | 通用 |
| `flashcards` | 问答卡片数组（可导出 Anki CSV） | 学生 |
| `quiz` | 单选/简答题 + 答案 + 解析 | 学生 |
| `meeting-minutes` | 议题 / 结论 / 待办（负责人/截止时间） | 白领 |
| `action-items` | 任务清单（原文依据） | 白领 |

**实现要点**：

- 检索策略：取文档前 N 块或按主题检索，输出必须带 `page/chunkIndex`，前端可跳转发源文档。
- 用 JSON Schema 约束 LLM 输出（`response_format` 或 Prompt + 后端清洗）；失败时降级为 Markdown。
- 前端在摘要页/新页面加「场景提炼」入口；结果以卡片/表格展示，支持复制与导出。
- 会议纪要类要明确「材料未提及负责人/时间时留空，不得编造」——与生成页「事实性条目不要 LLM 生成」的既有教训一致。

**风险**：LLM 生成测验题可能事实错误，需提供「原文出处」；输出结构化会拉长耗时，建议纳入 P1-4 任务中心。

**预估**：2-3 人日（共用一套管线）；每增加一个 kind 约 0.5 人日 Prompt/展示打磨。

### P1-3 生成排版增强与模板库

**现状**：`DocxRenderer` 固定「黑体标题 + 宋体正文」，无目录、页码、封面；输出只有 docx。

**方案**（由易到难）：

1. **目录 + 页码 + 页眉页脚**：python-docx 插入 TOC 域（`w:fldSimple` 或 `w:instrText`，用户打开 Word 按 F9 更新）；页脚页码；页眉文档标题。
2. **封面**：标题、副标题、作者/日期占位，作为模板的一部分。
3. **模板库**：在 `ai-service/templates/` 放若干 `.docx` 模板（公文/报告/论文），用占位符替换样式；`DocxRenderer` 接受 `template` 参数。或者先用代码内预设样式（更简单）。
4. **导出 PDF**：复用 LibreOffice headless 或前端调用浏览器打印；后端新增 `POST /api/generate/:fileId/pdf`。
5. **表格与图片块**：`SectionContent` 增加可选 `tables?: { headers, rows }[]` 与 `images?`，渲染器支持；assemble 契约向后兼容（缺省字段不影响旧调用）。
6. **风格/篇幅参数**：`style`（公文/报告/论文）+ `length`（简短/标准/详细），注入生成 Prompt。

**风险**：TOC 域在非 Word 阅读器（WPS/在线预览）中可能不自动刷新；LibreOffice 镜像体积与字体缺失会导致中文排版偏移，Docker 内需安装中文字体。模板与 assemble 契约同步要注意跨端类型。

**预估**：目录/页码/封面 2-3 人日；PDF 导出 1-2 人日；模板库与表格 3-5 人日。

### P1-4 统一任务中心 + 任务队列

**现状**：解析 fire-and-forget（重启靠 `recoverStaleParsingTasks` 兜底），转换同步阻塞，生成进度只在当前页面；没有取消、重试、历史。

**分两期**：

- **一期（2-3 人日，先解决可见性）**：新增 `tasks` 表（id、type: parse/convert/generate/import、file_id、status、progress、error、created_at/updated_at）；上传/转换/导入写任务；`GET /api/tasks` 列表 + `GET /api/tasks/:id`；前端顶栏「任务」抽屉，轮询 2s；失败可一键重试（复用现有入口）。
- **二期（5-8 人日，引入 BullMQ）**：backend 增加 worker 进程（同镜像、不同启动命令）；parse/convert/import 入队，带重试/退避/并发上限；取消 = 移除排队任务 + AbortController 断 HTTP；解析进度可让 ai-service 提供阶段事件（解压 / 分块 / 向量化）或按页回报。

**风险**：

- 队列化后 backend 变成 API + worker 双角色，部署与健康检查要同步改；任务与文件状态机要定义清楚（任务失败 vs 文件 failed）。
- LLM 流式生成无法真正中止上游（现有已知限制），取消只能断开连接；需在 UI 说明「已停止等待，后台可能已产生结果」。
- 解析进度若做到页级，需要把 ai-service `/ai/parse` 改成异步任务 + 查询/SSE，改动面较大，建议二期再评估。

**验收**：上传/转换/生成任务在任务中心可见；重启 backend 后未完成任务有明确状态；取消后不再占用并发。

### P1-5 混合检索 + 重排 + 问答反馈/评测

**现状**：纯向量检索（bge-small-zh）+ 固定阈值；没有质量度量，也没有用户反馈入口。

**方案分三步**：

1. **混合检索**：中文 BM25（jieba 分词）+ 向量检索，用 RRF 融合；标题命中加权。BM25 索引可按文档在解析时构建并缓存（内存或磁盘），无需新服务。
2. **重排（可选）**：对 top-N 候选用 CrossEncoder（如 bge-reranker-base）重排；模型较大（约 1GB），要评估内存与耗时，或先用「LLM 轻量重排」验证收益。
3. **反馈与评测**：
   - 新增 `qa_feedback` 表：message_id、rating（赞/踩）、comment、created_at；
   - 前端回答气泡加 👍/👎；
   - `ai-service/evals/` 放黄金集（20-50 个问题 + 期望出处），脚本计算 recall@k、引用页命中率、无答案时的拒答率；
   - 可选 LLM-as-judge 评估答案忠实度（faithfulness）。

**风险**：BM25 与向量分数的量纲不同，RRF 的参数要实验；重排模型与 embedding 模型会吃内存，注意 Docker 资源；评测集需要人工标注，别用 LLM 自动生成「标准答案」自欺欺人。

**预估**：混合检索 3-5 人日；重排 2-3 人日；反馈+评测 3-4 人日。

### P1-6 多文档综合摘要 / 综合大纲

**现状**：多文档问答已支持，但摘要/脑图仍只接受单 `fileId`；旧文档 3.5 的「多文档综合大纲」未落地。

**方案**：

- `/ai/summary` 与 `/ai/mindmap` 请求体增加 `fileIds?: string[]`（与 `fileId` 互斥，兼容旧契约）；backend 逐文件校验 `parsed` 并映射 aiFileId（复用 `requireParsed`）。
- 综合摘要：map-reduce——每篇先摘要，再合并生成「共同点 / 差异点 / 总体结论」；或检索式——按主题从各文档取块拼接。
- 综合大纲：titles 路径把各文档标题树平级合并（根节点为文件名，天然保留出处）；LLM 路径做主题归并并标注来源。
- 前端摘要页支持知识库多选（`KnowledgeBase` 已是多选），结果区标注「来自 N 篇文档」。

**风险**：文档数多时 token 爆炸，每篇取前 N 块并设置总文档上限；同名章节在 titles 合并下会并存，需在 UI 说明或提供归并模式。

**预估**：2-3 人日。

### P1-7 模型路由与成本面板

**现状**：设置页只有主模型/大纲模型两个槽位；没有 provider 故障转移、token 统计、费用估算。

**方案**：

1. **按功能分槽位**：`qa / summary / generate / outline / extract` 各自可配 provider（数据结构从 `mainProviderId/outlineProviderId` 升级为 `slots: Record<string, string|null>`，保留旧字段兼容迁移）。
2. **故障转移**：provider 配置增加「备用」列表；`LLMClient` 调用失败（限流/超时）后切换下一个，记录失败原因；设置页展示每个 provider 最近一次测试时间与延迟。
3. **用量统计**：捕获 OpenAI 响应的 `usage`（prompt/completion tokens；流式需 `stream_options.include_usage`，并非所有兼容网关都支持）。新增 `llm_usage` 表（时间、槽位、provider、model、tokens、耗时、成功/失败、缓存命中）；ai-service 当前对 PG 只读，要么改为可写该表，要么由 backend 代理上报——**建议 ai-service 写 `llm_usage`**，与 settings 只读互不影响。
4. **面板**：设置页或独立页展示按天/按功能的调用量、tokens、估算费用、平均延迟、失败率、缓存命中率。provider 可配置单价。

**风险**：不同 OpenAI 兼容网关的 usage 字段与流式支持不一致，缺失时按字符数估算并标注；成本面板是「估算」，不要给用户造成精确计费的错觉。API Key 目前明文存 PG，面板与备份要沿用部署指南的权限要求。

**预估**：4-6 人日。

### P1-8 网页链接导入

**方案**：

- 后端新增 `POST /api/import/url { url }`：校验 http/https、解析并拒绝内网/保留地址（**SSRF 防护**：解析 DNS 后校验 IP，限制重定向次数）、限制响应体大小与超时。
- 正文提取推荐 `trafilatura`（中文效果较好）或 `readability-lxml`；提取结果保存为 `.md` 到 `uploads/`，登记 `files` 并复用现有解析链路（依赖 P0-3 的 md/txt 支持）。
- 前端上传区增加「从链接导入」tab，粘贴 URL → 后台解析 → 知识库可见。
- 可选：支持「粘贴纯文本」直接入库（同样依赖 txt 支持），对会议记录/临时材料非常实用。

**风险**：SSRF 是硬性安全项；部分站点有反爬/登录墙，提取失败要给出明确提示；注意版权与 robots（个人工具可接受，公开产品需提示用户）。

**预估**：1-2 人日。

## 六、建议的落地路线

### 路线 A：优先做「用户立刻能感知」的体验闭环（推荐）

```text
第 1 批（约 1 周）：P0-1 扫描 OCR → P0-3 格式扩展 → P0-5 摘要导出 → P0-6 Docx 预览
第 2 批（约 2 周）：P0-2 全局搜索/免选择问答 → P0-4 会话持久化 → P1-4 任务中心（一期）
第 3 批（约 2 周）：P1-1 文档对比 → P1-2 场景提炼 → P1-3 排版增强
第 4 批（持续）：P1-5 检索质量/评测 → P1-7 成本面板 → P2-1 用户系统
```

逻辑：先修「扫描件不可用」这类信任问题，再补「文档多了找不到、刷新丢历史」的高频摩擦，最后做差异化的对比与场景提炼。

### 路线 B：面向演示 / 作品集叙事

优先级改为：**扫描 PDF OCR → 文档对比 → 学习卡/会议纪要 → 生成排版（目录/封面）→ PDF 引用高亮 → 评测面板**。这条线视觉冲击强、故事完整（读 → 问 → 比 → 写 → 评）。

### 路线 C：面向真实对外产品

先做 **P2-1 用户系统 + P1-4 队列 + P1-5 检索质量 + P1-7 成本与限额 + P2-8 生命周期治理**，再谈新功能。没有鉴权与任务可靠性之前，功能越多风险越大（部署指南已指出 8000 端口裸奔问题）。

## 七、通用落地约束（新增功能前必读）

除 `docs/功能拓展指南.md` 第 4 节的 17 条坑点外，本批扩展新增以下注意项：

1. **DB 变更走 Drizzle**：新增表/列必须改 `backend/src/db/schema.ts` 并生成迁移；`files.type/status` 是 text + CHECK，扩枚举要改约束而不是加 pgEnum。
2. **SSE 需要后端解析才能落库**：问答持久化/任务中心会打破「原样 pipe」，参考 `generate.service.ts` 的帧解析写法；解析失败也要保证连接正常结束。
3. **缓存 key 必须纳入新参数**：摘要长度/风格、对比维度、提炼类型等都要进 `llm_key`/`outline_key`，否则不同选项互相命中。
4. **新增 HTTP 调用要评估超时**：backend→ai-service 默认 120s；OCR、长文档 map-reduce、对比、PPT 都可能超时，必要时改 SSE 或任务化。
5. **Docker 新增系统依赖**：LibreOffice、中文字体、重排模型都会显著增大镜像；embedding/OCR 模型仍保持惰性加载，禁止 import 时加载。
6. **文件类型三处同步**：`FileType`（backend types）、DB CHECK、前端类型与上传 accept；图片 OCR 入口放开后要同步提示文案。
7. **多用户前不要扩大「全库」语义**：全局搜索/免选择问答默认全站可见，等 `user_id` 过滤落地后再对外开放。
8. **事实性内容禁止 LLM 编造**：场景提炼（会议纪要/待办）与生成文档一样，负责人、时间、数字必须以原文为依据，取不到就留空——这是已有文档明确记录过的教训。
9. **外部 URL 导入必须做 SSRF 防护**：校验协议、解析后 IP、限制重定向、超时与响应体大小。
10. **删除联动要覆盖新资产**：会话、任务、反馈、导出文件等新增数据在删除文件时必须同步清理或标记，避免孤儿数据。

## 八、不建议现在做（投入产出比低）

| 方向 | 原因 |
|------|------|
| 实时协同编辑 | 需要 CRDT/OT 与长连接基础设施，与当前「生成-下载」工作流不匹配 |
| 自研向量数据库 / 训练 embedding | bge-small-zh + chroma 已够用，收益远小于检索/分块工程优化 |
| 微调专属模型 | 没有足够标注数据；Prompt + 检索优化的 ROI 更高 |
| 完整 Office 在线编辑 | 与「AI 生成 + 导出」定位冲突，前端成本极高 |
| 复杂 RBAC/组织架构 | 先有基础登录与数据隔离，再谈角色权限 |
| 多端原生 App | PWA + 响应式足以验证需求 |
| 自托管大模型 | 成本、运维、效果都不占优；当前 OpenAI 兼容多供应商已足够灵活 |

## 九、实施记录（2026-10-19 起）

P0-1、P0-2 已于 2026-10-19 落地，P0-4 同日追加，P0-5 于 2026-10-24 落地。

### P0-1 扫描 PDF OCR 兜底

- `ai-service/app/core/parser.py`：`parse_pdf` 逐页取文本层，少于 `PDF_OCR_MIN_CHARS` 的页面用 PyMuPDF 以 `PDF_OCR_DPI` 渲染 PNG，复用 rapidocr 识别；OCR 页数超过 `PDF_OCR_MAX_PAGES` 直接报错，避免撞 backend 120s 超时。
- 新增配置（`app/config.py` + `.env.example`）：`PDF_OCR_MIN_CHARS=20`、`PDF_OCR_MAX_PAGES=30`、`PDF_OCR_DPI=200`。
- `parse_file` 增加统一兜底：整份文档没有任何可检索文本时抛 `ValueError`，状态落到 `failed`，不再出现「解析成功但问答报尚未解析」。
- **行为变化**：图片 OCR 失败、空文档也会明确失败；扫描页数超限时整份解析失败而不是部分成功（消息提示拆分文件）。
- **已验证**：用 PIL 生成无文字层的扫描 PDF（含“预算 128 万元”），`parse_file` 正确识别出文本；`PDF_OCR_MAX_PAGES=0` 时按预期报错。

### P0-2 知识库全局搜索 / 免选择问答

- ai-service：`core/rag.py` 新增 `search_chunks`（问题向量只编码一次、逐 collection top-3、合并排序、阈值过滤、Redis 缓存），新增 `app/api/search.py` 的 `POST /ai/search`，并在 `main.py` 注册。
- backend：新增 `services/search.service.ts` 与 `POST /api/files/search`；`qa.service.askStream` 在未传 `fileId/fileIds` 时自动取最近 50 篇已解析文档，实现全库问答。
- frontend：`QaPage` 知识库侧栏新增全局搜索框（300ms 防抖、点击结果选中文档并定位 PDF 页码）；未勾选文档时输入区提示「全库检索」，直接提问即全库问答。
- 限流：新增 `RATE_LIMIT_SEARCH_PER_MINUTE=60`（backend env + `.env.example`）。

### P0-5 摘要选项 + 结果导出（2026-10-24）

- **AI 服务**：
  - `core/rag.py` 新增 `SummaryOptions`（`brief/standard/detailed`、`paragraph/bullets`、可选 `focus`）与 `SummaryResult`；`/ai/summary` 接收 `length/style/focus`，返回 `summary/mode/totalChunks/coveredChunks/truncated`。
  - 长文档改 map-reduce：≤10 块单次调用；11-40 块按每 10 块分组并发摘要后合并；>40 块取 4 个均匀分布、首尾覆盖的连续窗口（共 40 块），`truncated=true`，并在合并 Prompt 中明确「抽样片段，不得声称覆盖全文」。
  - map 阶段 `ThreadPoolExecutor` 4 worker 单波并发；缓存 key、Redis 读写与配置读取全部留在主线程（`config_store` 的 psycopg2 连接非线程安全），worker 只做 LLM 调用。
  - 缓存升级为 v2：最终 key 纳入 mode/总块数/覆盖块数/length/style/focus/内容；分段摘要单独缓存（含 length/focus），单组失败重试可复用已成功分组。
  - `VectorStore.get_all` 改为按块 metadata `index` 排序（Chroma `get()` 顺序不保证），缺失 collection 明确报「尚未解析」而不是创建空集合。
- **backend**：`/api/qa/summary` 透传新参数，`qa.service` 先校验（非法值 400，不查 PG/不调 ai-service）；`SummaryResponse` 增加可选覆盖字段，ai-client 契约同步。
- **frontend**：摘要页新增篇幅/风格/重点关注选项；结果卡片显示生成选项快照与长文档覆盖说明，支持复制、下载 Markdown（Blob）与下载 Word（复用 `POST /api/generate/assemble`）；导出使用生成时快照，修改控件不会误导出旧结果。
- **已验证**：fake LLM 单测覆盖 1/10/11/40/41 块、single 与 map-reduce、首尾窗口、truncated、缓存命中与 key 分离、空输出报错、缓存/key 只在主线程；`/ai/summary` TestClient 验证非法参数 400 与响应字段；backend 运行中验证非法 length/style/focus 返回 400、合法选项进入文件校验（404）；三端类型检查通过（backend `npm run typecheck`、frontend `npx tsc --noEmit` / `npm run build`、`py_compile`）。
- **未验证**：真实 LLM 长文档端到端（会消耗 token）、前端复制/Markdown/Word 下载的人工点击验收。

### 已知限制

- 摘要超过 40 块时只均匀抽样 40 块；`focus` 只影响 Prompt，不参与抽样，重点内容可能落在未抽中的窗口。
- 摘要 map-reduce 仍是同步请求（受 backend→ai-service 120s 限制），未做 SSE 流式与取消；极端长文档仍可能超时。
- 相同参数的并发摘要请求可能同时 miss 缓存并重复调用 LLM（P0 接受）。
- 滚动升级时旧 ai-service 会忽略 `length/style/focus` 并返回默认摘要（覆盖字段缺省）；应先更新 ai-service，再更新 backend/frontend。
- OCR 仍在解析请求内同步完成，大扫描件受 30 页上限与 120s 超时约束；彻底解决依赖 P1-4 任务队列。
- 全局搜索逐 collection 串行检索，文档多时耗时线性增长；上限 50 篇是当前保护。
- 检索仍为纯向量 + 既有 min/floor 阈值；单文档场景下无强相关内容的 query 仍可能返回最近块，后续用 P1-5 的混合检索/重排优化。
- 会话暂无用户隔离（`conversations.user_id` 已预留）：P2-1 用户系统落地前，所有会话全站可见。
- 会话只在 `done` 帧后落库；落库失败不影响回答，但该轮可能在历史中缺失；客户端中途断开时本轮不保存。
- 历史窗口 20 条、会话列表上限 200 条（均未做分页/归档）。

## 附：一页版结论

如果只做三件事，按顺序：

1. **扫描 PDF OCR 兜底**——修复「解析成功但不可用」的信任问题，成本最低、收益最直接。
2. **知识库全局搜索 + 问答会话持久化**——让文档变多后仍然好用，把一次性工具变成可积累的知识工作台。
3. **文档对比 + 场景化提炼**——从「通用文档处理」走向具体场景，形成与普通聊天工具/网盘的差异。

其余功能按路线 A/B/C 的目标取舍。
